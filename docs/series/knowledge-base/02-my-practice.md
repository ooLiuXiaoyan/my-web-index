# 我的知识库实战手记：从 SaaS 验证到涉密内网私有化

<span class="badge badge-done">已发布</span> <span class="badge badge-wip">持续更新</span>

这是本系列最特殊的一篇——不讲别人的产品，讲我自己的项目。背景先交代：我所在的行业是测绘与地理信息，日常打交道的知识很「杂」：**文档（PDF 技术方案、合同）、GIS 矢量数据（河流、堤坝、测量标志）、关系型数据库、项目代码**。单位对数据安全要求高，部分场景是涉密内网。我的知识库之路走了四站，每一站都踩出了真实的坑，也沉淀了可复用的经验。

![知识库 RAG 流程原理图](/img/kb-rag-flow.png)

## 第一站：SaaS 快速验证（Coze / ima）

**目的**：花最小成本验证「知识库问答」在我们业务里到底有没有用。

用 Coze 和腾讯 ima 各搭了一个业务问答助手：上传几份技术规范 PDF，配个机器人，前后不到一小时。结论很快出来：**场景成立**——同事用自然语言问「某类项目要不要做地震安评」，比翻文件快得多。

但 SaaS 路线的天花板也立刻显现：

- **数据要上传云端**——我们的合同、涉密项目资料，这条路直接堵死
- **定制化受限**——切分策略、检索逻辑都不可控，遇到 GIS 数据这种非标格式更是无从下手

**经验**：SaaS 是最好的「场景验证器」，1 小时出结果，适合回答「要不要做」；但它回答不了「怎么做深」。

## 第二站：Cherry Studio 单机

场景验证通过后，第一步「正规化」是 Cherry Studio：本地客户端 + 本地模型，知识库总算留在自己电脑上了。

用了两个月，瓶颈变成**协作**：

- 知识库分散在每个人的电脑上，无法共享、无法统一管理
- 只能单机单轮对话，没法嵌入任何业务流程

**经验**：单机工具解决「我自己用」，解决不了「团队一起用」。知识库的价值随共享人数指数增长，孤岛式知识库是过渡形态。

## 第三站：Dify 私有化（涉密内网实战）

这是目前的主力方案：**完全离线运行的本地知识库**。

### 硬件与技术栈

| 项 | 配置 |
| --- | --- |
| 系统 | Ubuntu 22.04 LTS，内网局域网，涉密环境 |
| 内存 / 显存 | 32GB DDR4 / 8GB GDDR6 |
| 存储 | 500GB NVMe SSD |
| 模型推理 | Ollama 跑 DeepSeek-R1 7B（8GB 显存可跑） |
| 嵌入模型 | nomic-embed-text（768 维，Ollama 内直接运行，离线向量化） |
| 应用平台 | Dify（Docker 部署），管理知识库、Agent、工作流 |

### Cherry Studio → Dify 的六个升级点

1. **Web 化访问**：浏览器即开即用，团队统一 URL，不用每人装客户端
2. **团队协作**：多用户注册、知识库共享、权限分级
3. **工作流编排**：可视化拖拽，条件分支、多模型串联，重复业务流程自动化
4. **Agent 能力**：内置 ReAct / Function Calling，可调外部工具（数据库查询、GIS 分析）
5. **API 发布**：一键发布为 REST API，对接 OA、GIS 平台、小程序
6. **专业 RAG**：自定义分段、引用溯源、重排序、多知识库联合检索

### 落地的两个知识库

- **地震安评知识库**：5 份技术规范 + 50+ 文档片段，支持评审人员检索技术要求与案例参考。数据案例是康良路（京杭大运河—运溪路）工程的地震安全性评价报告，涵盖场地地震地质条件分析、地震动参数确定、地震地质灾害评价等章节
- **合同管理知识库**：3 类合同（技术服务 / 设备采购 / 工程承包）、12 个核心条款、30+ 文档片段，支持条款检索、对比分析、履约风险识别

**经验**：8GB 显存的消费级显卡 + 7B 模型，跑垂直领域知识库问答完全够用——**私有化的门槛比想象中低得多**，难的不是硬件，是知识治理（见第 07 篇）。

## 第四站：自建管线（PDF → ChromaDB）

Dify 用熟之后，我又回头自己写了一条管线，目的是**吃透底层 + 搞定非标数据**：

```
PDF → PyPDFLoader 提取 → RecursiveCharacterTextSplitter(500字符/块, 50重叠)
    → BAAI/bge-large-zh 向量化(768维) → ChromaDB(HNSW索引, 余弦相似度)
    → FastAPI 服务 → 问答演示页
```

首个实验对象是《浙江省测量标志保护改革技术方案》：可以问「保护措施有哪些」「改革目标是什么」，系统返回带相似度百分比和来源标注的答案，万级向量检索延迟 <100ms。

自建的价值很快体现——**Dify 处理不了的东西，自建可以**：我们的 GIS 数据（浙江河流线层、堤坝点层，GeoJSON/GDB 格式）在任何现成平台里都无法被正确解析，只能自己写管线。

## 未解决的硬骨头：GIS 数据怎么进知识库

目前 GIS 数据还以原始文件形式躺着，没进向量索引。自己梳理的四个核心问题：

1. GIS 数据未向量化，无法语义检索
2. 缺乏空间索引，无法做地理范围查询
3. 无法回答空间关系问题（「某坐标附近的水利设施」）
4. 空间属性与文本描述割裂，无法联合检索

改进方向已经想清楚（详见仓库里的 GIS 改进建议文档）：**文本语义检索 + 空间向量检索的混合架构**——把 GeoJSON 要素转成「文本描述向量 + 坐标向量 + Geohash」，用 RRF 融合排序，再往上是 Spatial RAG（意图识别 → 并行检索 → 融合 → GeoAI 生成带地图的回答）。这是第 07 篇质量工程之外、我给自己留的下一个课题。

## 下一站蓝图：「海纳」咨询知识库

正在规划的行业应用——重大工程地震安全性评价咨询知识库：

- **知识分层**：基础文档（什么是安评、主管部门、评价单位）→ 政策标准（触发条件、法规依据）→ 空间数据（断裂带、历史地震）→ 脱敏后的典型报告模板
- **智能体算子**：矢量数据查询、空间定位与分析、PDF 图表解析
- **六类场景**：是否需安评判断、费用估算、报告格式查询、图表样式查询、主管部门查询、评价单位/专家查询

## 四站走下来的经验总结

| 阶段 | 工具 | 解决什么 | 什么时候该升级 |
| --- | --- | --- | --- |
| 验证 | Coze / ima | 「要不要做」 | 数据敏感 or 要定制 |
| 单机 | Cherry Studio | 「我自己用」 | 要团队协作 |
| 私有化 | Dify + Ollama | 「团队在内网用」 | 要处理非标数据 |
| 自建 | ChromaDB 管线 | 「别人做不了的」 | 长期维护成本可承受 |

三条最想强调的：

1. **按数据敏感度选路线，不按功能列表选**：涉密单位从一开始就别在 SaaS 上浪费时间
2. **私有化门槛远低于想象**：一台 8GB 显存的机器就能跑起团队级知识库
3. **垂直行业的知识库没有现成答案**：GIS、图纸、专业报告这类数据，最终都要自己写管线——但先用平台把 80% 的通用场景跑起来，自建只补最后 20%
