# 核心能力拆解：桌面 Agent 的四大件

<span class="badge badge-done">已发布</span> <span class="badge badge-wip">定期刷新</span>

上一篇横评是按产品看的，这篇换个角度：**不看产品看能力**。所有桌面 Agent 的执行力都建立在四块积木上——本地文件读写、浏览器操作、定时任务、Office 集成。看懂这四件套的实现差异，评测任何新产品都能快速对号入座。

## 能力一：本地文件读写

桌面 Agent 与网页助手的本质区别。核心不在「能不能」，而在**授权模型**：

| 授权模式 | 含义 | 代表 |
| --- | --- | --- |
| 目录白名单 | 预先授权某些目录，范围内自由读写 | Claude Cowork 的工作目录 |
| 会话授权 | 本次对话内授权，结束后失效 | 豆包工作任务模式 |
| 单次确认 | 每个敏感操作单独弹窗确认 | 多数产品的删除/发送类操作 |

三条经验：

- **白名单适合高频固定场景**（工作目录），**单次确认适合危险操作**（删除、发送、支付）
- 授权粒度越细越安全，但弹窗越多体验越差——各家的取舍就在这里
- 读取几乎无害，**写操作才是风险分水岭**，重点关注产品对「覆盖、删除、外发」的二次确认设计

## 能力二：浏览器操作

三条技术路线，各有拥趸：

1. **云端浏览器**：任务在厂商的云沙箱里跑，与你的电脑隔离（ChatGPT Work）。安全、可无人值守，但登录态要单独处理，也碰不到你的本地环境
2. **接管你的浏览器**：以扩展形式操作你正在用的浏览器（Claude in Chrome、Browser Use）。能用你已有的登录态，但等于把浏览会话交给了 AI
3. **桥接模式**：Agent 本体在本地，通过桥接层驱动浏览器（Kimi WebBridge、WorkBuddy）。兼顾本地上下文与网页操作

**登录态是分水岭**：需要登录才能做的任务（查邮箱、操作内部系统），云端浏览器要重新登录甚至过验证码，接管式和桥接式直接继承你的会话——方便与风险同源。

## 能力三：定时任务

从「被动应答」到「主动打工」的关键一跃。看三个点：

- **触发方式**：固定周期（每 3 天）、指定时间（每天 9 点）、一次性（明早 8 点）——多数产品已支持 cron 级灵活度
- **结果交付**：本地生成文件是最基本的；更好的形态是**推送到 IM**（WorkBuddy 推到微信、豆包推到飞书），让结果来找你
- **断网与休眠**：Agent 跑在你自己电脑上时，关机休眠任务就停；云端方案（Copilot Studio Cloud PCs 等）才能真正 7×24

本站自己的实践：[AI 厂商图谱](../ai-vendors/)系列就用 GitHub Actions 定时任务每 3 天创建更新提醒——定时任务不一定要 AI 产品来做，**工程化方案往往更可靠**，这也是第 08 篇的主题。

## 能力四：Office 集成

分三个层次，别混为一谈：

- **生成**：一句话产出 Word / Excel / PPT 初稿——如今几乎家家都会，差距在排版质量
- **编辑**：在既有文件上修改，保持格式不崩——难得多，Kimi Work、豆包的 Office 本地集成主攻这里
- **协同**：AI 直接参与多人协作流（飞书 / 企微 / 钉钉内嵌 AI）——这是 IM 生态厂商的主场

另外注意「套件内嵌」与「独立 Agent」的分工：WPS AI、M365 Copilot 在自家套件内体验最顺，但跨软件任务（比如「把 Excel 数据做成 PPT 发到群里」）要靠独立桌面 Agent 或生态打通。

## 能力之外的隐藏变量

四大件之外，还有三个不写在宣传页上、但决定真实体验的变量：

1. **长任务稳定性**：任务跑 20 分钟会不会中途漂移？有没有断点恢复？这只能在实测中观察（见下一篇）
2. **多 Agent 并行**：Kimi Work 的 Agent 集群、WorkBuddy 的多窗口多 Agent——把大任务拆给多个智能体并行，提速明显，但**并行不等于可靠**，引用和数字仍需人工核对
3. **错误兜底**：遇到验证码、二次验证、弹窗干扰时的表现，是区分「演示产品」和「生产工具」的试金石

## 小结

| 能力 | 选型时问一句 |
| --- | --- |
| 文件读写 | 授权模型是哪种？写操作有二次确认吗？ |
| 浏览器操作 | 云端、接管还是桥接？登录态怎么处理？ |
| 定时任务 | 结果能推到 IM 吗？电脑休眠了怎么办？ |
| Office 集成 | 我要的是生成、编辑还是协同？ |
